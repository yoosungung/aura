# Aura 10년 지속 가능성 아키텍처 심층 점검 및 개선안

채택분은 계약·일정으로 승격했다. **지금 반영**: Command-State 분리 완화(컨택트·대화·FSM은 `svc-core` 동기 커밋), UUIDv7, Envelope(`schema_version`/`trace_id`/`causation_id`/`hop_count`), `conversations.version`, `account_sequences`, RLS InitPlan, ingestion 계층 정렬·단건 폴백·DLQ, Ego-Graph 2홉 `LIMIT 50`·Customer 역확장 금지. **P4–P7·출시 후**: 본문 Claim-Check·`contact_merged`, Capacity KV·`hop_count` 드롭, 임베딩 분리·Temporal edge·Cold Archive, 파티셔닝·Fair Queue. 정본은 [ARCHITECTURE.md](../ARCHITECTURE.md), [ROADMAP.md](../ROADMAP.md).

본 문서는 현재 [ARCHITECTURE.md](../ARCHITECTURE.md)와 [ROADMAP.md](../ROADMAP.md)에 정의된 설계가 **향후 10년(데이터 수십억 건, 테넌트 수천 개, AI 모델 세대교체, 글로벌/엔터프라이즈 규제 강화)** 동안 구조적 재작성(Rewrite) 없이 진화할 수 있는지 점검한 결과다.

현재 아키텍처는 **NATS 단일 백본**, **쓰기 경로 단일화(`svc-ingestion-worker`)**, **PG RLS 강제**, **클라이언트 생성 UUID 멱등성** 등 훌륭한 기본기를 갖추고 있다. 그러나 **비동기 적재 지연으로 인한 상태 역전(Race Condition)**, **10년치 시계열 데이터 누적에 따른 단일 테이블 팽창**, **임베딩 모델 하드코딩**, **온톨로지 그래프 노이즈 누적** 등 장기 운영 시 치명적인 병목과 결함이 내재되어 있다.

## 2. 영역별 심층 점검 및 아키텍처 개선안

### 2.1 [Critical] 일관성(Consistency)과 동시성(Concurrency) 결함

#### ① 비동기 배치 적재(100ms)와 동기 읽기의 충돌 (Read-Your-Own-Writes 및 FSM 경쟁)
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §1.2, §1.3, §5)**:
  * "`svc-core`는 이벤트 도메인을 읽기만 한다. FSM·배정·SLA 계산은 PG SELECT와 NATS Request-Reply로 수행하고, 전이는 `status_changed` 등 이벤트로 발행한다."
  * "상태 컬럼 갱신은 ingestion이 `status_changed`를 적용할 때만."
* **무엇이 깨지는가**:
  1. **FSM 이중 전이(Race Condition)**: 상담원 A가 티켓을 `resolved`로 전이 요청 → `svc-core`가 PG를 조회(`status = 'open'`) → 허용 판정 후 `status_changed(open -> resolved)` 이벤트 발행. **아직 `svc-ingestion-worker`가 PG에 반영하기 전(100ms 창 안)**에 자동화 규칙이나 상담원 B가 `open -> pending` 전이를 요청하면, `svc-core`는 여전히 PG에서 `open`을 읽고 이를 승인한다.
  2. **고객 첫 인입 시 FK/순서 역전**: 게이트웨이가 신규 고객 인입 시 `contact` 생성 이벤트, `conversation` 생성 이벤트, `message_created` 이벤트를 발행할 때, 혹은 `svc-core`에 대화 생성을 요청한 직후 메시지를 발행할 때 PG에 아직 부모 레코드(`contacts`, `conversations`)가 적재되지 않아 조회 실패 또는 FK 에러가 발생한다.
  3. **Read-Your-Own-Writes 실패**: 상담원이 메시지를 전송하거나 상태를 바꾼 뒤 화면을 새로고침(GET API 호출)하면, 아직 배치 플러시가 안 되어 이전 상태가 조회된다.
* **개선안**:
  * **선택지 A (권장 — Command-State 분리 완화 또는 낙관적 버전 관리)**:
    * `conversations` 테이블에 `version INT NOT NULL DEFAULT 1` (또는 `state_seq BIGINT`) 컬럼을 추가하고, `status_changed` 이벤트 페이로드에 `expected_version`을 명시한다.
    * `svc-core`는 대화별 최신 상태/버전을 NATS JetStream Key-Value(KV) 스토어(In-Memory/File backed) 또는 로컬 캐시+CAS(Compare-And-Swap)로 직렬화하여 검증하거나, **엔티티 생성(`contacts`, `conversations`) 및 FSM 상태 전이(`conversations.status`)에 한해서는 `svc-core`가 PG에 동기 트랜잭션(Transactional Outbox 또는 NATS 발행 결합)으로 선반영**하도록 계약을 정교화한다. (메시지·로그·온톨로지·첨부 등 고빈도 Append 데이터만 `svc-ingestion-worker` 배치 적재 유지)
  * **선택지 B (순수 이벤트 드리븐 유지 시)**:
    * NATS JetStream의 `Expect-Last-Subject-Sequence` 헤더를 사용해 `helpdesk.events.<acc>.<inbox>.<conv>.status_changed` 발행 시 스트림 레벨에서 동시 상태 전이를 원자적으로 거절(Optimistic Concurrency Control)한다.

#### ② 라운드로빈 및 Capacity 배정의 동시성 붕괴
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §2, [ROADMAP.md](../ROADMAP.md) P5)**:
  * "`svc-sla-routing`: 읽기. 전이는 이벤트", "온라인 + `C_current < C_max` 라운드로빈".
* **무엇이 깨지는가**:
  * 티켓 50개가 동시에 유입될 때 `svc-sla-routing`이 PG에서 `SELECT count(*) FROM conversations WHERE assignee_id = X AND status = 'open'`을 읽으면, `assigned` 이벤트가 PG에 적재되기 전까지는 `C_current`가 오르지 않는다. 결과적으로 한 상담원에게 50개가 전부 배정된다.
* **개선안**:
  * 상담원 가용 용량(`C_current`)과 라운드로빈 커서는 PG SELECT가 아니라 **NATS JetStream KV 버킷(`AGENT_CAPACITY`)**에서 원자적 증감(Atomic Revision Check)으로 관리하고, 주기적으로만 PG와 대사(Reconciliation)한다.

### 2.2 [Critical] `svc-ingestion-worker` 배치 적재의 부분 실패와 순서 역전

* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §2, §9)**:
  * "Pull 배치(500건 또는 100ms) 적재", "배치를 `account_id`로 묶고 그룹마다 위 트랜잭션을 연다."
* **무엇이 깨지는가**:
  1. **Poison Pill(독성 이벤트)로 인한 전체 배치 마비**:PostgreSQL은 트랜잭션 내 단일 구문이라도 에러(예: 삭제된 유저 참조 FK 위반, 잘못된 UTF-8 바이트, JSON 스키마 미세 불일치)가 나면 해당 트랜잭션 전체가 `ABORT`된다. 500건 중 1건이 불량이면 나머지 499건의 정상 테넌트 이벤트까지 무한 NACK → 재전송 루프에 빠진다.
  2. **이벤트 종류 간 토폴로지 순서**: 한 배치 안에 `conversation_created`와 `message_created`가 같이 들어오거나 멀티 워커 인스턴스에서 병렬 Pull 할 때, `messages` INSERT가 `conversations` INSERT보다 먼저 실행되면 `conversations(id)` 외래키 위반으로 실패한다.
* **개선안**:
  1. **티켓/대화 단위 파티셔닝 또는 적재 순서 강제**:
     * 배치 플러시 시 반드시 엔티티 계층 순서(`contacts` → `contact_inboxes` → `conversations` → `messages` → `attachments` → `status_changed/assigned`)대로 정렬하여 Upsert한다.
  2. **2단계 폴백(Fallback) 및 Dead Letter Queue(DLQ)**:
     * 배치(Bulk) 트랜잭션 실패 시 즉시 단건(또는 `SAVEPOINT`) 모드로 폴백하여 정상 이벤트를 커밋하고, 영구 실패(FK/데이터 오염) 이벤트는 `helpdesk.dlq.ingestion` 스트림 및 `ingestion_dead_letters` 테이블로 격리 후 ACK 처리한다.

### 2.3 [High] 10년 데이터 누적과 PostgreSQL 스토리지 아키텍처

10년 동안 하루 10만 건의 메시지만 쌓여도 `messages` 테이블은 **3억 6,500만 행**, `agent_tool_executions`와 `ontology_edges`까지 합치면 **수십억 행**에 달한다.

#### ① UUIDv4 기본값으로 인한 B-Tree 인덱스 파편화 (Index Bloat & Write Amplification)
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §10)**:
  * `DEFAULT gen_random_uuid()` (UUIDv4, 완전 난수) 및 발행자 생성 UUID.
* **무엇이 깨지는가**:
  * 테이블 크기가 RAM(Shared Buffers)을 넘어서는 순간(수천만 행 이후), 무작위 UUIDv4 PK는 매 INSERT마다 디스크의 임의 페이지를 읽고 수정(Random I/O + Full Page Write WAL 폭증)하게 만들어 `svc-ingestion-worker`의 500건 배치 속도를 10배 이상 떨어뜨린다.
* **개선안**:
  * **모든 UUID를 UUIDv7 (RFC 9562, 시간순 정렬 UUID)으로 강제**한다.
  * [ARCHITECTURE.md](../ARCHITECTURE.md) §1.7 계약사항을 *"발행자가 **UUIDv7**로 ID를 만든다"*로 개정하고, PostgreSQL 18+(내장 `uuidv7()`) 또는 `pg_uuidv7` 확장을 사용한다. 시간 지역성(Locality)이 보장되어 B-Tree 페이지 분할과 캐시 미스가 극적으로 줄어든다.

#### ② 시계열 대용량 테이블 파티셔닝(Partitioning) 부재
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §10)**:
  * `messages`, `attachments`, `agent_tool_executions`가 단일 비파티션 테이블이며 PK가 `(id)` 단독이다.
* **무엇이 깨지는가**:
  * PostgreSQL에서 나중에 무중단으로 파티셔닝을 도입하려면 **파티션 키(`created_at` 또는 `account_id`)가 반드시 PRIMARY KEY 및 모든 UNIQUE 제약조건에 포함**되어야 한다. 지금 `PRIMARY KEY (id)`로 고정하면 3년 뒤 파티셔닝 전환 시 전체 스키마와 외래키를 뜯어고쳐야 한다.
  * 또한 10년 후 오래된 테넌트 데이터를 아카이빙(`DELETE`)할 때 수천만 행 `DELETE`는 Autovacuum 마비와 테이블 블로트를 유발한다(`DROP PARTITION`이나 `DETACH PARTITION`이어야 즉시 정리 가능).
* **개선안**:
  * UUIDv7을 쓰면 `id` 자체에 타임스탬프가 내장되므로 **Range Partitioning by `id` (또는 `created_at`)**가 가능해진다.
  * 대용량 3대 테이블(`messages`, `attachments`, `agent_tool_executions`)은 P1부터 월별/분기별 파티셔닝이 가능하도록 PK를 복합키로 설계하거나 UUIDv7 범위 파티션 구조를 채택한다.

#### ③ `conversations.display_id` 채번 병목과 충돌
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §10)**:
  * `display_id INT NOT NULL, CONSTRAINT uq_conversation_display UNIQUE (account_id, display_id)`
* **무엇이 깨지는가**:
  * `display_id`는 테넌트(`account_id`)별로 `1, 2, 3...` 증가하는 번호다. 게이트웨이나 `svc-ingestion-worker`가 `SELECT COALESCE(MAX(display_id), 0) + 1`로 채번하면 동시 인입 시 `uq_conversation_display` 충돌이 상시 발생한다.
* **개선안**:
  * `account_sequences (account_id UUID PRIMARY KEY, last_conversation_display_id BIGINT NOT NULL DEFAULT 0)` 카운터 테이블을 두고, 대화 적재 시 `INSERT ... ON CONFLICT (account_id) DO UPDATE SET last_conversation_display_id = account_sequences.last_conversation_display_id + 1 RETURNING last_conversation_display_id`로 원자적 채번한다. (자료형도 `INT` 대신 `BIGINT` 권장)

#### ④ 스키마 세부 결함 (Soft Delete, 연락처 다중 식별자, 메시지 편집/반응)
* **`ON DELETE CASCADE`의 위험성**: `accounts`, `inboxes`, `contacts`에 모두 `ON DELETE CASCADE`가 걸려 있다. 관리자가 실수로 인박스를 지우거나 컨택트를 병합/삭제하는 순간 수만 건의 대화·메시지·감사로그가 물리 삭제되며 복구 불가능한 DB 락이 걸린다. → 핵심 마스터 테이블에는 `deleted_at TIMESTAMPTZ` (Soft Delete) 및 비동기 청소를 도입해야 한다.
* **고객 병합(Contact Merge)**: 옴니채널에서는 한 고객이 처음엔 익명 웹챗(`contact A`), 나중엔 이메일(`contact B`), 나중엔 카카오(`contact C`)로 인입된 뒤 동일인으로 밝혀지는 일이 매일 발생한다. `contacts` 병합 시 대화·인박스·온톨로지 노드를 이관하는 `contact_merged` 이벤트와 `merged_into_contact_id` 필드가 필요하다.

### 2.4 [High] AI & 온톨로지 계층의 10년 진화성

향후 10년간 가장 급격히 변할 영역은 **LLM과 임베딩 모델**이다.

#### ① `vector(1536)` 컬럼 하드코딩의 함정
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §10, [ROADMAP.md](../ROADMAP.md) 미결정)**:
  * `articles.embedding vector(1536)`, `ontology_nodes.embedding vector(1536)`.
  * "embedding 차원 1536은 계약이므로 바꾸면 DDL도 바꾼다."
* **무엇이 깨지는가**:
  * 10년 동안 임베딩 모델은 최소 4~5번 바뀐다(1536차원 → 3072차원 → Matryoshka 가변 차원 → 멀티모달 벡터 등).
  * 본 테이블(`ontology_nodes`, `articles`)에 `vector(1536)`이 박혀 있으면:
    1. 모델을 교체할 때 구버전 벡터와 신버전 벡터를 동시에 유지하며 무중단 백필(Shadow Re-indexing)할 수 없다.
    2. 어떤 행이 어떤 모델(`text-embedding-3-small` vs 차세대 모델)로 임베딩되었는지 추적할 메타데이터(`model_name`, `model_version`)가 없다.
    3. HNSW 인덱스가DDL에서 누락되어 있어 현재 스키마로는 Sequential Scan이 발생한다.
* **개선안**:
  * 임베딩을 엔티티 본 테이블에서 분리하여 **`embeddings` 전용 테이블(또는 모델 버전별 파티션)**로 관리하거나, 최소한 `embedding_model VARCHAR(100)`, `embedding_version INT` 컬럼과 `halfvec`(pgvector 0.7+ 메모리 50% 절감) 및 HNSW 부분 인덱스를 표준화한다.

#### ② Ego-Graph 온톨로지의 무한 팽창과 사실 충돌 (Temporal Graph 부재)
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §8, §10)**:
  * 대화 종결(`resolved`) 시마다 `ontology_nodes`와 `ontology_edges`를 추출해 적재한다.
  * 1~2홉 조회 쿼리에는 `LIMIT`도 없고 시간 유효성 필터도 없다.
* **무엇이 깨지는가**:
  1. **슈퍼노드(Supernode) 폭발**: `entity_type = 'Product'`(예: "주력 요금제")나 주요 `PainPoint`(예: "결제 실패") 노드는 수만 명의 고객(`Customer`)과 연결된다. 고객 A에서 1홉(`Product` "프로 플랜")으로 간 뒤 **2홉(`hop2`)을 조회하는 순간, "프로 플랜"을 쓰는 다른 고객 수만 명의 노드·엣지가 한꺼번에 조인**되어 쿼리가 폭발하고 프롬프트 컨텍스트가 오염된다!
     * *코드 검증*: [ARCHITECTURE.md](../ARCHITECTURE.md) §8의 SQL을 보면 `hop1`이 양방향(`source_node_id = c.id UNION ALL target_node_id = c.id`)이고, `hop2`가 `e.source_node_id = h.node_id`다. 만약 공용 노드가 `source`가 되는 엣지가 있으면 타 고객 데이터나 수천 개 엣지가 딸려 나온다.
  2. **시간에 따른 사실 변화(Temporal Contradiction)**: 2026년에는 고객이 `PREFERS -> 이메일 상담`이었는데, 2029년에는 `PREFERS -> 카카오톡 상담`으로 바뀌었다. 현재 스키마는 과거 엣지를 만료시킬 방법이 없어 상충되는 두 사실이 영원히 프롬프트에 주입된다.
* **개선안**:
  1. **Ego-Graph 2홉 쿼리 제한 및 정렬**:
     * 2홉 탐색 시 `entity_type = 'Customer'`로의 역방향 확장을 금지(`WHERE n.entity_type != 'Customer'`)하고, `weight`와 최신성 기준 `ORDER BY weight DESC, updated_at DESC LIMIT 50`을 강제한다.
  2. **Temporal Edge 도입**:
     * `ontology_edges`에 `valid_from TIMESTAMPTZ`, `valid_until TIMESTAMPTZ` (NULL이면 현재 유효), `confidence FLOAT`, `last_observed_at TIMESTAMPTZ`, `source_conversation_id UUID`를 추가해 사실의 노후화(Decay)와 대체를 지원한다.

### 2.5 [High] NATS 단일 백본의 한계와 보완책

#### ① NATS 페이로드 크기 제한 (기본 1MB, 최대 권장 8MB)
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §1.1, §4)**:
  * 모든 이벤트와 Request-Reply가 NATS를 통과한다.
* **무엇이 깨지는가**:
  * 이메일 채널(`gateway-email`)이나 풍부한 HTML 아티클, 긴 대화 스레드 조회(Request-Reply)는 본문 텍스트와 인라인 이미지만으로도 쉽게 1MB를 초과한다. NATS `MaxPayload` 에러로 인입 자체가 드롭될 수 있다.
* **개선안**:
  * **Claim Check 패턴 명문화**: 페이로드가 256KB를 초과하는 원시 MIME 이메일이나 대형 본문은 게이트웨이가 Object Storage(MinIO/S3)에 먼저 저장하고, NATS 이벤트에는 `content_ref_url`과 요약본만 실어 보낸다.

#### ② 90일 보존 제한(`--max-age 90d`)과 감사/재처리(Replay)의 모순
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §3)**:
  * `CONVERSATIONS_STREAM`은 `--max-age 90d --discard old`다.
* **무엇이 깨지는가**:
  * 91일 이전의 이벤트는 영구 소멸된다. 향후 새로운 분석 뷰나 AI 그래프 재구축을 위해 과거 이벤트를 Replay하려 해도 불가능하며, 금융/엔터프라이즈 고객사의 법적 감사 로그 보존 의무(3~5년)를 충족할 수 없다.
* **개선안**:
  * NATS JetStream에는 Hot 데이터(30~90일)만 유지하되, 별도의 아카이빙 컨슈머(또는 Bento/Vector 등)가 `helpdesk.events.>`를 **Object Storage(S3/MinIO)에 날짜별 Parquet/JSONL(Cold Event Archive)**로 영구 적재하는 파이프라인을 추가한다.

#### ③ 스키마 진화(Schema Evolution) 전략 부재
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §4)**:
  * JSON Envelope에 `"id"`, `"type"`, `"occurred_at"`, `"payload"`만 존재하고 **스키마 버전(`schema_version`)**이 없다.
* **개선안**:
  * Envelope에 `"schema_version": 1` 필드를 필수화하고, `contracts/`의 JSON Schema 변경 시 **Backward & Forward Compatibility(필드 삭제 금지, 필수 필드 추가 시 기본값 지정)** 규칙을 `ARCHITECTURE.md` §1에 못 박는다.

### 2.6 [Medium] 멀티테넌시, RLS 성능 및 운영 안정성

#### ① PostgreSQL RLS의 대량 쿼리 성능 저하와 복합 인덱스
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §9, §10)**:
  * `USING (account_id = NULLIF(current_setting('app.current_account_id', true), '')::uuid)`
  * 일부 인덱스(`idx_conversations_assignee_open`, `idx_messages_conv_created`, `idx_contact_inboxes_lookup`)에 `account_id`가 빠져 있다.
* **무엇이 깨지는가**:
  * RLS가 켜진 테이블을 조회할 때 PostgreSQL 플래너는 모든 쿼리에 `account_id = ...` 필터를 강제 주입한다. 이때 인덱스의 선두(또는 포함) 컬럼에 `account_id`가 없으면 불필요한 Heap Fetch가 급증한다.
  * 또한 `current_setting(...)`이 매 행마다 호출(Volatile 평가)되지 않도록 `(SELECT NULLIF(current_setting('app.current_account_id', true), '')::uuid)` 형태의 **InitPlan 서브쿼리 래핑**을 써야 PostgreSQL 옵티마이저가 상수로 캐싱한다.
* **개선안**:
  * 모든 RLS 정책 식을 `USING (account_id = (SELECT NULLIF(current_setting('app.current_account_id', true), '')::uuid))`로 변경한다(대량 스캔 시 CPU 30~50% 절감).
  * 모든 핵심 인덱스에 `account_id`를 복합 구성한다.

#### ② 테넌트 간 Noisy Neighbor (특정 테넌트의 큐 독점)
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §3)**:
  * 모든 테넌트가 단일 `TASKS_STREAM`(`helpdesk.tasks.>`)과 단일 `CONVERSATIONS_STREAM`을 공유한다.
* **무엇이 깨지는가**:
  * 대형 테넌트 A가 프로모션 장애로 1분간 10만 건의 문의와 웹훅을 쏟아내면, WorkQueue 뒤에 줄 선 중소 테넌트 B, C의 AI 추론(`tasks.ai.reasoning`)과 아웃바운드 발송(`tasks.outbound.*`)이 수십 분간 지연된다.
* **개선안**:
  * Task 서브젝트에도 `<account_id>`를 포함(`helpdesk.tasks.<domain>.<account_id>.<action>`)시키고, 워커에서 테넌트별 Fair Queuing(Token Bucket / 동시 실행 세마포어)을 적용해 한 테넌트가 워커 풀의 N% 이상을 점유하지 못하게 격리한다.

### 2.7 [High] 보안, 개인정보보호(GDPR/개보법) 및 관측성(Observability)

#### ① 개인정보 파기(Right to be Forgotten)와 불변 이벤트 로그의 충돌
* **무엇이 깨지는가**:
  * 한국 개인정보보호법 및 유럽 GDPR은 고객 탈퇴/요청 시 개인정보(이름, 이메일, 전화번호, 대화 내 민감정보)의 즉각 파기를 요구한다.
  * 그러나 NATS `CONVERSATIONS_STREAM`에는 90일간 불변 이벤트로 평문 PII가 남아 있고, `svc-ingestion-worker`를 통해 적재된 백업에도 남는다.
* **개선안**:
  * **Crypto-Shredding (암호화 파기) 또는 Subject Purge**:
    * NATS 서브젝트가 `helpdesk.events.<account_id>.<inbox_id>.<conversation_id>.*` 구조이므로, 고객 파기 요청 시 해당 고객의 `conversation_id` 서브젝트들을 `nats stream purge --subject`로 즉시 삭제할 수 있는 운영 API를 `svc-core`에 둔다.
    * 장기적으로는 민감 필드(전화번호, 이메일, 본문)를 고객/테넌트별 키(DEK)로 암호화하고 파기 시 키를 삭제하는 구조를 고려한다.

#### ② 정적 `pubsub_token` 영구 사용 문제
* **현재 설계 ([ARCHITECTURE.md](../ARCHITECTURE.md) §10, [ROADMAP.md](../ROADMAP.md) 마지막 줄)**:
  * `users.pubsub_token VARCHAR(255) UNIQUE NOT NULL`, `contact_inboxes.pubsub_token VARCHAR(255) UNIQUE NOT NULL`.
  * "Auth와 무관하게 `users.pubsub_token` / `contact_inboxes.pubsub_token` 계약은 유지한다."
* **무엇이 깨지는가**:
  * DB에 저장된 고정 문자열 토큰이 한 번이라도 브라우저 로그나 네트워크 스니핑으로 유출되면 만료 시각(TTL)이 없어 영구적으로 실시간 이벤트를 도청할 수 있다.
* **개선안**:
  * DB의 `pubsub_token`은 시드(Seed) 또는 회전 가능한 식별자로만 쓰고, 실제 WebSocket 연결에는 **짧은 만료 시간(예: 1시간)을 가진 서명된 토큰(JWT 또는 PASETO)**을 발급하여 검증한다.

#### ③ 분산 트레이싱(Distributed Tracing) 컨텍스트 전파 누락
* **무엇이 깨지는가**:
  * HTTP/gRPC 없이 NATS로만 6개 서비스(`gateway` → `NATS` → `svc-core` / `ingestion` / `sla-routing` / `automation` / `ai-agent` → `outbound`)가 얽혀 돌아가면, 장애나 루프(Automation Rule이 이벤트를 발행하고 그 이벤트가 다시 Automation Rule을 트리거하는 무한 루프!) 발생 시 원인을 추적할 수 없다.
* **개선안**:
  * 이벤트 Envelope 및 NATS 헤더에 **`trace_id` (W3C TraceContext)**, **`causation_id` (이 이벤트를 유발한 직전 이벤트 ID)**, **`correlation_id`**, **`hop_count` (무한 루프 차단용, 예: `hop_count > 5`면 자동화 중단)**를 필수 계약으로 추가한다.

## 3. 즉시 반영을 권장하는 구체적 변경 명세 (Actionable Diffs)

코드 한 줄 없는 **지금(P0 직후, P1 착수 전)** 반영하면 비용이 0에 가깝지만, P3 이후에 고치려면 수개월이 걸리는 핵심 변경안이다.

### 3.1 이벤트 Envelope 개정안 ([ARCHITECTURE.md](../ARCHITECTURE.md) §4 대상)

```json
{
  "id": "0192d4f0-8c00-7000-8000-111111111111",
  "schema_version": 1,
  "type": "message_created",
  "occurred_at": "2026-10-28T05:00:00Z",
  "account_id": "0192d4ef-0000-7000-8000-aaaaaaaaaaaa",
  "inbox_id": "0192d4ef-0000-7000-8000-bbbbbbbbbbbb",
  "conversation_id": "0192d4ef-0000-7000-8000-cccccccccccc",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "causation_id": "0192d4f0-8b00-7000-8000-000000000000",
  "hop_count": 1,
  "payload": {}
}
```
* **변경 포인트**:
  1. 모든 ID는 **UUIDv7** 포맷.
  2. `schema_version` 추가로 향후 10년간 페이로드 하위 호환 진화 보장.
  3. `trace_id`, `causation_id`, `hop_count` 추가로 관측성 확보 및 `svc-automation` ↔ `svc-ai-agent` 간 무한 이벤트 루프 원천 차단.

### 3.2 DDL 개정 핵심 포인트 ([ARCHITECTURE.md](../ARCHITECTURE.md) §8, §9, §10 대상)

```sql
-- 1. RLS 정책 최적화 (InitPlan 캐싱 적용)
CREATE POLICY <t>_tenant ON <t>
  USING (account_id = (SELECT NULLIF(current_setting('app.current_account_id', true), '')::uuid))
  WITH CHECK (account_id = (SELECT NULLIF(current_setting('app.current_account_id', true), '')::uuid));

-- 2. 테넌트별 안전한 display_id 채번 테이블
CREATE TABLE account_sequences (
    account_id UUID PRIMARY KEY REFERENCES accounts(id) ON DELETE CASCADE,
    last_conversation_display_id BIGINT NOT NULL DEFAULT 0
);

-- 3. conversations에 낙관적 동시성 제어용 version 추가
ALTER TABLE conversations ADD COLUMN version INT NOT NULL DEFAULT 1;

-- 4. ontology_edges에 시간 유효성(Temporal) 및 출처 추적 추가
ALTER TABLE ontology_edges
    ADD COLUMN confidence FLOAT NOT NULL DEFAULT 1.0,
    ADD COLUMN source_conversation_id UUID REFERENCES conversations(id) ON DELETE SET NULL,
    ADD COLUMN valid_from TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    ADD COLUMN valid_until TIMESTAMPTZ;

-- 5. Ego-Graph 2홉 쿼리 시 타 고객 노드 오염 방지 및 상한(LIMIT) 강제
-- hop2 조건에 AND n.entity_type != 'Customer' 및 valid_until IS NULL, LIMIT 50 추가
```
