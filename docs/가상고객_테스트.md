LangWatch Scenario 시뮬레이터 발화를 채널 규격(REST, 웹훅, SMTP)으로 넣고, 에이전트 답을 **같은 채널 아웃바운드**에서 읽어 반환한다. 실행기는 pytest가 아니라 [`virtual-client/`](../virtual-client/DESIGN.md) 프로세스다. Scenario는 채널을 모르며 `AgentAdapter.call()`만 본다.

인입은 NATS에 직접 넣지 않고 `gateway-web` / `gateway-kakao` / `gateway-email`만 친다. 회신은 상담원 Application API가 아니라 고객이 받는 경로다. 기본 주소는 클러스터 NodePort다. 웹 `http://127.0.0.1:30080`(nginx→`gateway-web`, `/public` 포함), 카카오 `30081`, SMTP `30025`. `go run ./cmd/gateway-*`는 `--base http://127.0.0.1:8080 --kakao-base http://127.0.0.1:8081 --smtp-port 2050`.

## 전체 아키텍처 흐름

```
[LangWatch User Simulator]
          │ (문자열 발화)
          ▼
   ┌───────────────┐
   │ virtual-client│ ── 1. Web:   gateway-web Client API POST
   │ Channel       │ ── 2. Kakao: gateway-kakao POST /cstalk/message
   │ Adapters      │ ── 3. Email: gateway-email SMTP DATA
   └───────────────┘
          │
          ▼
[Aura gateway-* → NATS → ingestion / svc-core / svc-ai-agent]
          │ 조회는 테넌트 mcp_servers.url → virtual-client 모의 MCP
          │ 인입 ACK ≠ 회신. 답은 채널 아웃바운드
          ▼
   ┌───────────────┐
   │ Response      │ ── Web:   Client API GET messages
   │ Extractor     │ ── Kakao: 가짜 허브 POST /cstalk/plain
   │               │ ── Email: AURA_SMTP_RELAY(Mailpit) 수신함
   └───────────────┘
          │
          ▼
[LangWatch Judge / Next Turn]
```

인입과 회신은 같은 TCP 연결이 아니다. 카카오 웹훅·SMTP DATA 응답은 접수 ACK다. 웹은 외부 허브가 없어 `gateway-web` Client API가 곧 고객 채널이다.

| 채널 | 인입 | 고객이 받는 회신 |
|------|------|------------------|
| Web | `gateway-web` `POST .../messages` | 같은 게이트웨이 `GET .../messages` |
| Kakao | `gateway-kakao` `POST /cstalk/message` | `AURA_KAKAO_API_URL/cstalk/plain` |
| Email | `gateway-email` SMTP DATA | `AURA_SMTP_RELAY` MIME |

카카오 가짜 허브는 `AURA_KAKAO_API_URL=http://127.0.0.1:18081`. 이메일은 Mailpit을 릴레이에 둔다. compose에는 둘 다 없다. Mailpit 기본 SMTP는 `1025`, Aura 기본 릴레이는 `2525`이므로 포트를 맞춘다.

```sh
mailpit --smtp 0.0.0.0:2525 --listen 0.0.0.0:8025
```

카카오 세션이 꺼져 있거나 서킷이 열려 있으면 허브/릴레이에 아무 것도 안 온다. 그때 티켓에만 남은 답을 상담원 API로 읽으면 안 된다. 고위험 환불은 승인 카드 뒤에만 MCP가 나가므로, virtual-client Counselor가 admin으로 `POST .../tools/{execution_id}/approve`만 한다. Judge는 그 경로를 쓰지 않는다.

모의 운영계는 in-process stub(`paid`/`in_transit` 고정)을 덮어쓴다. bootstrap이 `POST /api/v1/accounts/{id}/mcp_servers`에 `http://127.0.0.1:18082/mcp`를 등록한다. `svc-ai-agent`는 도구 목록을 캐시하므로 등록 후 재시작한다.

최신 Scenario API는 `scenario.AgentAdapter` + `await scenario.run(agents=[adapter, UserSimulatorAgent, JudgeAgent])`다. CLI와 어댑터 구현은 [virtual-client/DESIGN.md](../virtual-client/DESIGN.md) `## Commands`.

```sh
./virtual-client/run.sh --channel web --scenario lost-package --max-turns 8
./virtual-client/run.sh --channel all --scenario all
```

## 시나리오

픽스처 id는 CLI `--scenario`다. 시뮬레이터는 턴이 끝나거나 Judge가 멈출 때까지 발화를 이어 보낸다.

### cancel-in-transit — 배송 중 취소

- persona: "주문번호는 없지만 방금 주문한 물건을 즉시 취소하고 싶어하는 성격 급한 고객"
- goal: "주문 취소 또는 반품 처리 방법을 최종 안내받는 것"
- mock: 주문 존재, `shipping=in_transit` → 단순 취소 불가, 반품 안내
- criteria:
    - "에이전트가 배송 및 주문 상태 확인을 위해 주문번호 또는 고객 정보를 요청했는가?"
    - "배송 시작 후에는 단순 취소가 불가능하고 반품 절차를 밟아야 함을 안내했는가?"
    - "고객의 재촉에 정중하게 안내를 완료했는가?"

### lost-package — 배송 조회 및 오도착 분쟁 (Syncora)

- persona: "외부 이동 중 모바일로 문의하여 주문번호를 모른 채, 어제 도착했어야 할 옷이 안 왔다며 다짜고짜 화를 내는 조급한 고객"
- goal: "내 주문 상태(배송 완료 여부)를 파악하고, 물건이 문 앞에 없음을 알려 분실 확인 또는 재배송/환불 접수를 받아내는 것"
- mock: 전화/이름으로 주문 특정, `shipping=delivered`
- criteria:
    - "에이전트가 주문번호 부재 시 휴대폰 번호 또는 이름 등 대체 식별 정보를 요청해 주문을 특정했는가?"
    - "시스템 상 '배송 완료' 상태임을 명확히 안내하고, 고객 미수령 주장에 맞춰 배송 기사 확인 또는 분실 사고 접수를 진행했는가?"
    - "고객의 일방적인 재촉에도 절차(확인 후 처리)를 차분하고 명확하게 설명했는가?"

### return-fee — 반품 배송비 분쟁 (Bitext)

- persona: "신발 사이즈 미스로 반품하려다 왕복 배송비 6천 원 차감 안내를 보고 '무료배송 사기'라며 소비자원 고발을 운운하는 공격적인 고객"
- goal: "배송비 차감에 대해 강력히 항의하다가, 사이즈 교환 시 배송비 조건을 확인한 후 교환 접수로 변경 완료하는 것"
- mock: 왕복 6천 원 정책, 교환 시 배송비 조건
- criteria:
    - "에이전트가 단순 변심 반품 시 왕복 배송비 발생 정책을 약관 근거와 함께 정중히 설명했는가?"
    - "고객의 법적 대응/신고 위협 발언에 감정적으로 맞서지 않고 공감 및 완화 화법을 구사했는가?"
    - "고객이 '교환'으로 의도를 바꿨을 때 이를 정확히 포착하여 교환 배송비 및 맞교환 절차를 안내했는가?"

### damaged-exchange — 파손품 맞교환 및 품절 대안 (Polaris)

- persona: "배송받은 유리 디퓨저가 깨져 상자까지 젖은 상태라 즉각 동일 제품 맞교환을 원하는 차분하지만 단호한 고객"
- goal: "파손 사진 증빙을 제출하고 교환을 요청했으나, 해당 향 품절 시 타 제품 변경 대신 즉시 취소/환불 확정을 받는 것"
- mock: 배송완료 + SKU 품절 → 환불 분기
- criteria:
    - "에이전트가 파손에 대해 사과하고 안전 주의를 당부하며 파손 사진 증빙을 명확히 요청했는가?"
    - "사진 확인 후 재고 부족(품절) 상황을 투명하게 안내하고 대체 선택지(타 향 변경 vs 전액 환불)를 제시했는가?"
    - "고객의 환불 선택 시 깨진 제품의 폐기 안내(회수 생략)와 함께 결제 취소 접수를 완료했는가?"

### coupon-retro — 프로모션 쿠폰 소급 적용 (aitrainingdatabroker)

- persona: "주문 완료 직후 10% 신규 할인 쿠폰(WELCOME10)을 누락한 것을 발견하고 결제 차액(15,000원)만 부분 환급받고 싶어 하는 알뜰한 고객"
- goal: "카드 부분 취소 가능 여부를 확인하고, 불가능할 경우 포인트/적립금 대체 지급 또는 주문 취소 후 재주문 경로를 안내받는 것"
- mock: 주문 ID·`WELCOME10`·차액 15000, PG 부분취소 불가 → 적립금/재주문
- criteria:
    - "에이전트가 고객의 주문 ID, 결제 수단, 쿠폰 코드 정보를 누락 없이 식별했는가?"
    - "결제 후 쿠폰 사후 적용(PG 부분 취소) 가능 여부 정책을 명확히 안내했는가?"
    - "단순 거절에 그치지 않고 대안(재주문 안내 또는 적립금 수동 지급 접수)을 제시했는가?"
