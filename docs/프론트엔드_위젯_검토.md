# Aura 10년 지속 가능성 점검 — `frontend/` 및 `packages/widget-sdk/` 심층 검토 및 개선안

본 문서는 현재 [`frontend/`](../frontend/)와 [`packages/widget-sdk/`](../packages/widget-sdk/)가 **향후 10년(엔터프라이즈 B2B 헬프데스크 환경, 하루 수만 건의 상담 처리, 다양한 고객사 호스트 환경 및 브라우저 보안 정책 변화)** 동안 구조적 재작성(Rewrite) 없이 유지·확장될 수 있는지 점검한 아키텍처 및 UI/UX 분석 보고서다.

정본 계약은 [ARCHITECTURE.md](../ARCHITECTURE.md), 일정은 [ROADMAP.md](../ROADMAP.md), 각 컴포넌트의 현재 내부 설계는 [frontend/DESIGN.md](../frontend/DESIGN.md) 및 [packages/widget-sdk/DESIGN.md](../packages/widget-sdk/DESIGN.md)를 따른다.

## 1. 총평 및 위험도 요약 매트릭스

## 2. 왜 현재 `frontend/` UI/UX가 낙후되어 보이는가? (원인 진단과 해결책)

현재 [`frontend/`](../frontend/)는 **"TDD 시나리오 검증을 위해 API 1개당 `<form>` 1개를 화면에 직렬 배치한 테스트 하네스"** 상태다. 하루 8시간 이상 수백 건의 티켓을 처리하는 상담원(Agent)의 인지 부하와 작업 속도를 고려한 워크스페이스 설계가 빠져 있다.

### 2.1 정보 계층(Information Hierarchy)의 붕괴

#### ① 좌측 대기열(`nav.queue`)에 관리자 설정 폼이 동거함
* **현상 ([`App.jsx`](../frontend/src/App.jsx))**:
  * `administrator` 권한으로 로그인하면 좌측 `320px` 대기열 상단에 [`InboxMembers`](../frontend/src/components/InboxMembers.jsx), [`InboxHmac`](../frontend/src/components/InboxHmac.jsx), [`CatalogSettings`](../frontend/src/components/CatalogSettings.jsx)가 세로로 렌더링된다.
  * 정작 가장 중요한 **실시간 상담 대기열(`queue`)은 스크롤 한참 아래로 밀려나 보이지 않는다.**
* **개선안**:
  * **좌측 글로벌 네비게이션 레일(Navigation Rail, `56px`) 도입**: `[인박스 워크스페이스]` 뷰와 `[관리자 설정(Settings)]` 뷰를 완전히 분리한다.
  * 인박스 멤버 관리, HMAC 시크릿 열람/회전, 라벨 카탈로그, 저장응답, 공유 매크로 관리는 설정 화면에서만 렌더링한다.

#### ② 중앙 스레드(`section.thread`)의 5단 폼 나열과 대화창 압착
* **현상 ([`App.jsx`](../frontend/src/App.jsx))**:
  * 대화를 클릭하면 메시지 타임라인(`ol.log`) 위에 [`AssignTicket`](../frontend/src/components/AssignTicket.jsx), [`SnoozeTicket`](../frontend/src/components/SnoozeTicket.jsx), [`TicketLabels`](../frontend/src/components/TicketLabels.jsx), [`TicketMacros`](../frontend/src/components/TicketMacros.jsx)(매크로 생성 폼 포함), [`ResolveTicket`](../frontend/src/components/ResolveTicket.jsx)이 각각 독립된 블록으로 쌓인다.
  * 하단에도 [`TicketAttachments`](../frontend/src/components/TicketAttachments.jsx), [`InternalNote`](../frontend/src/components/InternalNote.jsx), 답장 `form.composer`가 3단으로 나뉘어 있어, 정작 대화를 읽어야 할 `ol.log` 영역이 화면 중앙에 좁은 틈처럼 남는다.
* **개선안**:
  * **상단 단일 헤더 액션바(Header Action Bar, 높이 `52px`)**:
    * 좌측: 티켓 번호(`#display_id`), 고객 식별자/이름, 채널 배지(`web` / `email` / `kakao`), 현재 상태 배지(`open` / `pending` / `snoozed`).
    * 우측: `[담당자 배정 Popover]`, `[스누즈 프리셋 Popover]`, `[매크로 실행 Dropdown]`, `[대기 | 해결 버튼 그룹]`을 한 줄의 툴바로 압축한다.
  * **우측 컨텍스트 패널(Context Pane, `280px`~`320px`) 분리**:
    * 티켓 라벨 부착/제거([`TicketLabels`](../frontend/src/components/TicketLabels.jsx)), 고객 메타데이터, 향후 P7에서 들어올 **Living Profile(Ego-Graph 1~2홉 카드)**을 우측 3번째 패널(3-Pane의 우측 영역)에 배치한다.

### 2.2 데이터베이스 지향적 입력 UX (Raw UUID / ISO 문자열 직접 타이핑)

* **현상**:
  * [`AssignTicket.jsx`](../frontend/src/components/AssignTicket.jsx): 상담원 목록 선택이 아니라 `담당자 ID` 인풋에 UUID를 직접 타이핑해야 한다.
  * [`SnoozeTicket.jsx`](../frontend/src/components/SnoozeTicket.jsx): `스누즈 시각` 인풋에 RFC3339 문자열(`2026-10-30T18:00:00Z`)을 직접 타이핑해야 한다.
  * [`InboxMembers.jsx`](../frontend/src/components/InboxMembers.jsx), [`InboxHmac.jsx`](../frontend/src/components/InboxHmac.jsx): `인박스 ID`와 `상담원 ID`를 직접 입력한다.
* **개선안**:
  * **배정**: 현재 인박스의 멤버 목록(`listInboxMembers`)을 불러와 이름/이메일 기반 `<Select>` 또는 검색 가능한 Combobox + `"나에게 배정(Assign to me)"` 원클릭 버튼을 제공한다.
  * **스누즈**: `"1시간 뒤"`, `"오늘 오후 6시"`, `"내일 오전 9시"`, `"다음 주 월요일"` 프리셋 버튼 + `<input type="datetime-local">` 폴백을 제공한다.

### 2.3 메시지 타임라인과 컴포저(Composer)의 시각적 구분 부재

* **현상**:
  * 메시지 로그(`ol.log`)가 단순 텍스트 `<li>` 나열이어서 **고객 인입 메시지(Incoming)**, **상담원 대고객 답장(Outgoing)**, **내부 메모(Private Note)**가 한눈에 구분되지 않는다.
  * 답장 입력창(`composer`), 내부 메모 입력창(`InternalNote`), 첨부 업로더(`TicketAttachments`)가 3개의 폼으로 쪼개져 있어 상담원이 시선을 계속 옮겨야 한다.
* **개선안**:
  * **메시지 버블 디자인 시스템**:
    * 고객(`senderType === "Contact"`): 좌측 정렬, 뉴트럴 서피스 배경(`bg-slate-100 text-slate-900`).
    * 상담원(`senderType === "User"`, `private === false`): 우측 정렬, 프라이머리/인디고 톤(`bg-zinc-900 text-white` 또는 브랜드 컬러).
    * 내부 메모(`private === true`): 앰버/옐로 노트 카드(`bg-amber-50 border border-amber-200 text-amber-950`) + 상단 `"내부 메모 (고객에게 보이지 않음)"` 캡션.
    * 첨부파일: 단순 URL 문자열 대신 파일명·크기·아이콘 카드(이미지는 썸네일 미리보기)로 렌더링.
  * **하단 통합 컴포저(Unified Composer)**:
    * 하나의 에디터 컨테이너 상단에 `[답장 (Reply)]` / `[내부 메모 (Note)]` 모드 전환 탭을 두고, 메모 모드일 때는 에디터 배경색 전체가 연한 앰버 톤으로 바뀌어 오발송 사고를 원천 방지한다.
    * 파일 첨부 버튼(클립 아이콘)을 컴포저 하단 바에 통합하고, `/` 슬래시 명령어(`canned_responses`) 팝오버를 에디터 바로 위에 띄운다.

### 2.4 스타일 시스템 이원화 해소
* **현상 ([`styles.css`](../frontend/src/styles.css))**:
  * Tailwind CSS v4를 도입했음에도 [`styles.css`](../frontend/src/styles.css)에 레거시 CSS 클래스(`.workspace`, `.queue`, `.thread`, `.assign`, `#ddd` 보더, `font-family: sans-serif`)가 하드코딩되어 있어 shadcn/ui 컴포넌트와 디자인 톤이 충돌한다.
* **개선안**:
  * CSS 변수 기반 시맨틱 디자인 토큰(`--background`, `--foreground`, `--muted`, `--border`, `--primary`, `--warning`)과 Pretendard / Inter 폰트 스택을 적용하고, 레이아웃을 Tailwind 유틸리티 및 shadcn 프리미티브로 일원화한다.

## 3. `packages/widget-sdk`를 iframe으로 하는 것이 좋은가?

### 3.1 결론: **"호스트 경량 로더 + 교차 출처(Cross-Origin) iframe 본체" 아키텍처가 10년 후에도 정답이다**

외부 고객사 웹사이트에 임베딩되는 서드파티 라이브챗 위젯을 설계할 때 선택지는 크게 3가지다:
1. **호스트 DOM 직접 마운트 (CSS prefixing)**
2. **Web Components (Shadow DOM) 단독**
3. **경량 호스트 로더 + `iframe` 격리 (현재 Aura의 방향)**

10년 장기 운영 관점에서 **3번(로더 + iframe)이 유일하게 엔터프라이즈 보안과 호환성을 만족**한다.

| 비교 항목 | Web Components (Shadow DOM 단독) | 경량 로더 + `iframe` (Aura 채택) |
|---|---|---|
| **JS 메모리 및 토큰 보안** | **취약.** 호스트 페이지와 `window` 전역 컨텍스트를 공유하므로, 호스트 사이트 XSS 발생 시 Contact Bearer 토큰과 대화 내역이 즉시 탈취됨 | **완벽 격리.** `helpdeskOrigin`과 호스트 origin이 분리되어 브라우저 SOP(Same-Origin Policy)가 토큰과 WS 연결을 보호함 |
| **호스트 전역 오염 방어** | **취약.** 고객사 사이트가 `window.fetch`, `Array.prototype`, `Zone.js` 등을 오염시켰을 때 위젯 런타임이 함께 깨짐 | **완벽 방어.** iframe 내부는 독립된 `window`와 표준 Web API를 가짐 |
| **CSS/스타일 격리** | Shadow DOM으로 격리되나 `rem` 단위(호스트 `html { font-size: 62.5% }`) 및 상속 폰트/변수 영향을 받음 | 문서 자체가 분리되어 100% 일관된 렌더링 보장 |
| **고객사 CSP(보안 정책) 충돌** | 호스트 사이트의 `connect-src`, `script-src`, `style-src`에 헬프데스크 도메인을 일일이 허용해야 함 | 호스트는 `frame-src`(및 로더 스크립트)만 허용하면 되고, WS/API 통신은 iframe 내부 origin(`self`)으로 수행되어 CSP 마찰 최소화 |
| **서드파티 쿠키 폐지 영향** | 호스트 도메인 컨텍스트에 종속됨 | Aura는 쿠키가 아닌 `postMessage` 시드(`pubsub_token`) → `/public/api/v1/inboxes/{id}/auth` Bearer 교환 방식이므로 서드파티 쿠키 차단(Safari ITP 등)에 영향받지 않음 |

### 3.2 현재 [`packages/widget-sdk`](../packages/widget-sdk/) iframe 구현의 4가지 문제점과 개선안

iframe 방식 자체는 옳으나, 현재 코드는 **단일 고정 iframe**으로만 작성되어 있어 실무 투입 시 다음 문제가 발생한다.

#### ① 호스트 페이지 클릭 가림(Pointer-Events Trap) 현상
* **문제 ([`loader.js`](../packages/widget-sdk/src/loader.js))**:
  * `iframe` 하나를 생성해 `document.body.appendChild(iframe)` 하고 있다.
  * 만약 이 iframe이 채팅창 크기(`380px × 640px`, `position: fixed; bottom: 20px; right: 20px`)를 가진 상태에서 내부 UI만 접혀 있으면, **투명한 iframe 사각형 영역 아래에 있는 고객사 웹사이트의 버튼·링크가 모두 클릭 불가능**해진다.
* **개선안 (Hybrid Launcher 패턴)**:
  * **방안 A (권장 — 런처 버튼은 호스트(Shadow DOM), 채팅창 본체는 iframe)**:
    * 우측 하단 플로팅 런처 버튼(`56×56px`)과 안 읽은 메시지 배지는 `loader.js`가 작은 Shadow DOM 컨테이너로 렌더링한다.
    * 사용자가 버튼을 클릭해 위젯을 열었을 때만 채팅 본체 `iframe`을 표시(또는 `pointer-events: auto; opacity: 1`)한다.
  * **방안 B (단일 iframe 동적 리사이즈)**:
    * 이미 [`loader.js`](../packages/widget-sdk/src/loader.js)에 `msg.event === "resize"` 핸들러가 있으므로, 닫힌 상태에서는 iframe을 `64px × 64px`(`border-radius: 9999px`)로 축소하고, 열린 상태에서는 `380px × 680px`(모바일 뷰포트에서는 `100vw × 100dvh`)로 즉시 리사이즈하도록 `loader.js` 기본 스타일과 `frame.js` 이벤트를 연결한다.

#### ② 설계 문서([`DESIGN.md`](../packages/widget-sdk/DESIGN.md))와 실제 코드([`frame.js`](../packages/widget-sdk/src/frame.js))의 토큰 교환 불일치
* **문제**:
  * [ARCHITECTURE.md](../ARCHITECTURE.md) §1.10 및 [packages/widget-sdk/DESIGN.md](../packages/widget-sdk/DESIGN.md)에는 *"Contact `pubsub_token`은 시드다. 프레임이 `POST /public/api/v1/inboxes/{inbox_id}/auth`로 짧은 만료 접근 토큰을 받는다"*고 명시되어 있다.
  * 그러나 현재 [`frame.js`](../packages/widget-sdk/src/frame.js)는 `init` 이벤트로 받은 `token`을 `/auth` 교환 없이 그대로 `Authorization: Bearer`와 `/ws?token=`에 사용하고 있다.
* **개선안**:
  * `init` 수신 시(또는 첫 API/WS 호출 전) 시드 토큰으로 `/public/api/v1/inboxes/${inboxId}/auth`를 호출해 단기 HMAC `access_token`을 발급받고, 만료 시 자동 재교환하도록 수정한다.

#### ③ 메시지 전송 시마다 WebSocket이 중복 생성되는 버그
* **문제 ([`frame.js`](../packages/widget-sdk/src/frame.js))**:
  * [`send(content)`](../packages/widget-sdk/src/frame.js) 함수가 호출될 때마다 `connectWS()`를 무조건 호출하여, 고객이 메시지를 5번 보내면 동일한 WebSocket 연결이 5개 중첩 생성되고 수신 메시지가 5번씩 중복 렌더링된다.
* **개선안**:
  * `socket`이 이미 `OPEN` 또는 `CONNECTING` 상태이고 토큰이 바뀌지 않았으면 재연결하지 않으며, 토큰 갱신으로 재연결할 때는 기존 `socket.close()`를 먼저 호출한다.

#### ④ 실제 `/widget.html` 엔트리 및 번들 파이프라인 부재
* **문제**:
  * `loader.js`는 `{helpdeskOrigin}/widget.html`을 로드하지만, 저장소에 실제 고객용 채팅 화면을 그리는 `widget.html`과 번들 빌드 스크립트가 없다.
* **개선안**:
  * 호스트 삽입용 단일 IIFE/ESM 번들(`aura-loader.min.js`, 5KB 미만, Zero dependency)과 iframe 내부용 `widget.html` + UI 스크립트 빌드 파이프라인을 구성한다.

## 4. `frontend/` 코드 레벨 결함 상세 (즉시 수정 필요 항목)

### 4.1 [`store.js`](../frontend/src/store.js) — 실시간 메시지 수신 시 대화 메타데이터 유실
* **위치**: [`frontend/src/store.js`](../frontend/src/store.js) `applyRealtime()`
* **원인**:
  `message.created` 이벤트를 처리할 때 `nextConv` 객체를 새로 만들면서 기존 `prev` 대화 객체의 `status`, `version`, `assigneeId`, `snoozedUntil` 필드를 복사하지 않는다:
  ```js
  const nextConv = {
    ...prev, // <-- 현재 코드에 이 스프레드가 누락됨
    id: convId,
    inboxId: event.inbox_id || prev?.inboxId,
    contactId: payload.contact_id || prev?.contactId,
    contactInboxId: payload.contact_inbox_id || prev?.contactInboxId,
    lastContent: content,
    unread: selected ? 0 : (prev?.unread ?? 0) + 1,
    labels: prev?.labels || [],
  };
  ```
* **영향**:
  실시간 메시지가 도착한 직후 상담원이 해당 티켓을 해결(`ResolveTicket`)하거나 배정(`AssignTicket`)하려 하면 `conversation.version`이 `undefined`로 초기화되어 `expectedVersion: 1`로 전송되고, 백엔드 `svc-core`의 CAS 버전 검증(`expected_version != current_version`)에 걸려 실패한다.

### 4.2 [`gateway.js`](../frontend/src/gateway.js) — 15분 후 모든 HTTP 요청이 실패하는 인증 단절
* **위치**: [`frontend/src/gateway.js`](../frontend/src/gateway.js) 및 [`frontend/src/App.jsx`](../frontend/src/App.jsx)
* **원인**:
  1. HTTP API 함수들이 `res.status === 401`일 때 `/auth/refresh`를 호출해 새 토큰을 받아 재시도하지 않는다.
  2. WebSocket이 닫혀서 `connect()` 내부에서 `refresh()`로 새 토큰을 받아도 `App.jsx`의 `session.token` 상태를 업데이트하는 콜백(`onTokenRefreshed`)이 없다.
* **해결책**:
  * 공통 `requestWithAuth(session, path, init, deps)` 헬퍼를 두어 `401` 발생 시 Single-flight(동시 다발적 요청이 와도 `refresh`는 1번만 수행)로 토큰을 갱신하고 `onSessionUpdate` 콜백으로 `App` 상태를 동기화한다.

### 4.3 10년 장기 유지보수를 위한 프론트엔드 엔지니어링 표준화
1. **스키마 드리븐 타입 생성 (`contracts/` → TypeScript)**:
   * [`contracts/`](../contracts/)의 JSON Schema로부터 TypeScript 인터페이스(`MessageCreated`, `StatusChanged` 등)를 자동 생성하여 백엔드(`backend/internal/contracts`)와 프론트엔드가 단일 진실 공급원(SSOT)을 공유하게 한다.
2. **키보드 퍼스트(Keyboard-First) 상담 경험**:
   * 숙련된 상담원은 마우스를 거의 쓰지 않는다. `J`/`K`(큐 위아래 이동), `R`(답장 창 포커스), `N`(내부 메모 포커스), `⌘+Enter`(전송), `E`(해결 처리), `⌘+K`(명령 팔레트/매크로 즉시 실행) 단축키 체계를 내장한다.
3. **가상 리스트(Virtualization) 및 낙관적 업데이트(Optimistic UI)**:
   * 답장 전송 시 서버 응답을 기다리는 동안(Pending) 메시지 버블을 즉시 투명도 70%(`status: "sending"`)로 표시하고 실패 시 `[재전송]` 버튼을 노출한다.
